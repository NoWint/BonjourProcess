CSP 安全策略完全禁用
tauri.conf.json · 安全
"csp": null 完全禁用了内容安全策略，WebView 可加载和执行任意来源的脚本。结合 Tauri 的系统级 API 权限，XSS 攻击者可完全控制用户系统。
建议：配置严格 CSP，仅允许本地资源和必要 CDN
敏感凭证明文存储于数据库
001_initial.sql · 安全
access_token、refresh_token、littleskin_access_token 在 SQLite 中以明文存储，无任何加密。任何能访问数据库文件的程序均可窃取用户认证令牌。
建议：AES-256-GCM 加密，密钥由 OS Keychain / DPAPI 管理
LittleSkin 密码明文传输到后端
auth.rs · 安全
littleskin_login 命令将用户密码以明文参数从前端传递到 Rust 后端，密码会出现在 Tauri IPC 日志和调试器中。
建议：前端先对密码做哈希/加盐处理，或使用 OAuth 流程
数据库初始化失败仅记录日志不退出
lib.rs · 可靠性
init_database() 失败后仅 tracing::error，应用继续运行。后续所有数据库操作将 panic 或返回错误，用户无法得到清晰提示。
建议：初始化失败应阻止应用启动，或进入安全恢复模式
高优与中等问题
前端状态管理严重过度集中（God Component）
App.tsx · 架构
AppContent 包含 20+ 个 useState，承载所有全局状态，约 770 行代码。任何状态变更触发整棵树重渲染。
建议：引入 Zustand / Jotai，按领域拆分 Store
Tauri Bridge 层大量 any 类型滥用
tauri-bridge.ts · 类型安全
约 60+ 处 API 返回类型使用 any，包括 searchModsGlobal、batchInstallMods 等核心功能。完全丧失编译期类型安全。
建议：为每个 Command 定义 TS 返回类型，可用 ts-rs 从 Rust 自动生成
数据库全局互斥锁导致并发瓶颈
repository.rs · 性能
所有 Repository 共享 Arc<Mutex<DatabaseConnection>>，任何数据库操作都会锁住整个连接。高频操作互相阻塞。
建议：使用 r2d2 连接池或 tokio::task::spawn_blocking + 多连接
前后端数据模型双重维护
types/index.ts vs models/ · 一致性
前端 TS 类型和后端 Rust struct 完全手动维护两套，字段命名风格不一致（snake_case vs camelCase），且 LauncherSettings 默认值前后端不一致。
建议：使用 ts-rs 或 specta 从 Rust struct 自动生成 TS 类型
游戏会话时间记录逻辑错误
App.tsx · 数据准确性
startTime: endTime - 60000 硬编码为结束时间减 60 秒，duration 永远是 1 分钟，完全不反映真实游戏时长。
建议：游戏启动时记录真实 startTime，退出时计算实际时长
大量 Tauri Command 为空实现（Stub）
auth.rs 等 · 功能完整性
microsoft_login_refresh、upload_skin、upload_avatar 等核心功能返回 unsupported 错误，但前端仍暴露这些 API。
建议：前端对未实现功能做 UI 层屏蔽；优先实现 token 刷新
Tauri invoke_handler 注册了 200+ 个命令
lib.rs · 编译效率
单一 generate_handler! 宏注册了约 200 个命令，编译时间极长，增量编译效率低。
建议：按模块拆分为多个 handler 注册组，使用宏简化
网络请求缺少重试和超时策略
network.rs · 健壮性
HTTP Client 全局超时 300 秒，无重试机制；get_version_manifest 仅在多源间线性切换。网络不稳定时可能阻塞 5 分钟。
建议：实现指数退避重试；按区域延迟动态选择源
MicrosoftAuthService 每次调用都创建新实例
auth.rs · 性能
MicrosoftAuthService::new() 在每个命令中创建新的 reqwest::Client，无法复用连接池。每次认证请求都建立新 TCP 连接。
建议：将 MicrosoftAuthService 作为 Tauri managed state 单例
前端 loadInitialData 串行加载
App.tsx · 启动性能
设置、账户、版本清单、已安装版本、游戏会话、更新检查等 6 个独立请求串行执行。启动加载时间 = 所有请求延迟之和。
建议：使用 Promise.allSettled 并行加载独立数据
ProcessGuardian 每次查询都创建 System 实例
process_guardian.rs · 性能
get_running_processes 和 is_process_alive 每次调用都 sysinfo::System::new() + refresh_processes。系统进程扫描开销大，频繁调用导致 CPU 占用高。
建议：维护一个共享的 System 实例，定时刷新而非每次创建
缺乏前端路由系统
App.tsx · 架构
页面切换完全依赖 currentPage 状态 + 条件渲染，无 URL 映射，无浏览器历史。无法通过 URL 直接导航到特定页面。
建议：引入轻量路由（如 react-router 的 MemoryRouter）
